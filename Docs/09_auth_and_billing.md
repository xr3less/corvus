## 1. Authentication

| Aspect                   | Choice                                                                                                             | Why                                                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| Method                   | Discord OAuth2 only (V1)                                                                                           | Only identity our users all have; one click; no passwords to breach. Recovery email attached at signup for lockout/account-loss cases |

| Team access (V1 minimal) | Owner-only until V1-2+ (Editor matrix deferred — one invite row exists in no table yet; tracked in PLAN)           | Full matrix (viewer/audit) is V2                                                                                                      |

## 4. Webhooks & edge cases

Creem webhook route is BUILT, test-mode (`apps/web/app/api/webhooks/creem/route.ts`): HMAC-SHA256 of the raw body + receipt-first idempotency (`webhook_receipts.event_id` PK, `INSERT_RECEIPT_SQL` at route.ts:444-446) + exactly-once credit grant keyed on the payment identity (`INSERT_GRANT_SQL` at route.ts:466-470, covered by 0011's partial unique index on `(ref_id, reason, attempt)`). Only `subscription.paid` (and one-time `checkout.completed`) may touch the ledger; `subscription.active` and the rest are access/status only (`isCreditEvent` at route.ts:144-150). The tables it writes exist in the working tree, unmerged (`apps/gateway/drizzle/0011_credit_ledger_subscriptions.sql`: `credit_ledger`, `subscriptions`, `webhook_receipts`); the join key is `metadata.accountId`, never the email (route.ts:43-46). Trial creates NO Creem object — trial state lives in our DB only; the first Creem event for a user is the upgrade checkout (D-034). Missed-event safety (nightly reconciler comparing Creem subscription state vs local `subscriptions` table) is STILL ABSENT — no reconciler file, cron, or pg_cron job exists on disk (only comment references at route.ts:95,700); treat §4's old reconciler sentence as a plan, not a build. Allowance grants are ledger rows, never in-memory flags. Failed renewal → plan stays until period end, then falls back to sleep (NEVER deletes). Dispute → freeze AI spend, keep bot online, human review within 3 business days (MoR SLA).

## 5. Security & compliance notes

Sensitive data lives in: Postgres (OAuth IDs, configs, XP — EU box), secret store (tokens, encrypted), Creem (cards — WE NEVER TOUCH THEM), logs (no tokens, no message content). We explicitly do NOT store: card numbers, Discord passwords, member message content (unless an opted-in behavior needs it, then per-guild retention + owner-visible toggle). GDPR minimum: Privacy + Terms pages exist and are already honest about the money path — privacy (`apps/web/app/privacy/page.tsx:79-81,117-119`) says card handling "isn't live yet" and bills via Creem only when billing ships; terms (`apps/web/app/terms/page.tsx:82-85,89-90`) says payments aren't live, no checkout, no charges, and names the live 3-day trial. The dashboard links both (privacy → `/dashboard`; terms → delete-from-dashboard), but no account export/delete ENDPOINT exists in `apps/web/app/api/` yet — dashboard-side see/export/delete and a DPA page are still plans, claimed by §5/privacy copy but with no route behind them. Sub-processors listed (Contabo/Hetzner, Creem, AI providers), 72h breach notice, access/delete via dashboard + support email.
